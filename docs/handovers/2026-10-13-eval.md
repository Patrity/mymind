# Outcome judge + eval substrate (cycle 85)

Two gaps closed: a workstream could claim "done" without having done it, and nobody could tell
whether a prompt/model/tool change made Bridget better or worse. This cycle adds an **outcome
judge** that verifies every `finish_workstream` (Task 1), and an **eval substrate** — isolated
Postgres-schema-per-world "eval worlds" with a fake Gmail/Calendar/web/sandbox (Task 2), a runner +
matcher/scorer + CLI + the seed suite `bridget-core` (Task 3), and an `/evals` dashboard (Task 4) —
plus a whole-branch final review and one fix wave (Task 5) that closed five deploy-blocking capacity
risks the per-task reviews couldn't see because each task only looked at its own slice. Current-state
reference: [`wiki/eval.md`](../wiki/eval.md); the verifier itself is documented in
[`wiki/judge.md` § Outcome judge](../wiki/judge.md#outcome-judge).

**Status: built, awaiting deploy.** Every gate is green, two live dev baselines were measured, and
the final re-review found no new Critical/Important breakage — but prod acceptance (§ below) has not
been run, and six new Minor findings from that re-review are parked as backlog, not fixed.

## What shipped, by task and fix round

**Task 1 — outcome judge** (`64dec51`, `d5f80c8`; fix round 1 `8e99d15`): `judge/outcome.ts` —
`verifyOutcome(evidence)`, one tool-free `generateText`+`Output.object` call on the `judge` chain, 60 s
budget, never throws; evidence = goal + summary + the workstream's own tool-call log (≤ 60 calls) +
a read-only offline workspace diff (≤ 8 KB) + children's own states/summaries/verifications for a
coordinator, every part but a top-level goal fenced untrusted. `met` at confidence ≥ 0.7 finishes;
otherwise send back (max 2) with the gaps, then finish `done` **flagged**. `workstreams.verification`/
`send_backs` (migration 0084), `stateDetail: 'verifying'`, a ⚠ badge, `judge:outcome` activity rows,
and thread notes per send-back. Fix round 1: a child's goal is fenced (coordinator-authored, model
output, not Tony's words); a CAS miss is told the current count rather than incrementing twice; the
final segment (or no budget left) always finishes flagged rather than ever producing `failed`;
`verifying` now wins over `evaluating` in `stateDetail` instead of either clearing the other;
send-backs reset to 0 on resume of a failed/cancelled workstream; a low-confidence `met` shows "⚠
unverified," not "⚠ met."

lock `85086`) with a per-run token budget (`eval.maxTokensPerRun`, default 5,000,000) and a UI
confirm above 50 attempts; a forbidden approval now fails the case exactly like a forbidden action;
drift checked **before and after** each attempt; the deploy cancels running evals before migrating;
world builds use short per-statement locks instead of one long transaction; image/limits probes are
cached process-wide; the workstream's own verification verdict is read into eval results (closing
the gap where the eval couldn't show what Task 1 actually measures); and one `activity_log` summary
row per finished run (`kind: 'eval'`, tokens/duration/pass-rate, no case content). A second re-review
(`final-rereview-1.md`) confirmed every finding addressed with no new Critical/Important breakage,
and surfaced six new Minors (N1–N6, §Backlog) — none blocking, all parked.

## Deviations from the spec, and key rulings

1. **Isolation: one Postgres schema per eval world, not an `eval_run_id` column** (Task 2's own
   decision per the plan's "decide by blast radius" instruction; spec §3.2 had left this open). A
   column needs a new filter in every list/search/MCP/home/digest/cron read path, forever, and a
   future migration's table starts **unfiltered** by default — exactly the kind of thing that gets
   missed under time pressure. A schema needs none of that: every table is enumerated and shadowed
   automatically at world-build time, Tony's queries run on the default `search_path` and physically
   cannot see a world's rows, and cleanup is one `DROP SCHEMA … CASCADE`. The final review's own
   isolation walk-through (§ below) found no path from a world to any of Tony's real data as a
   result — not a close call, a structural one.
2. **Host `exec` is refused outright inside an eval world**, not merely gated behind a card (Task 2
   review C1; spec had assumed the scripted approver would be enough). The review found this would
   otherwise let a case's model run real shell commands with real secrets on the real host, through
   nothing more than an approval the case itself controls. Now `exec`'s handler refuses before
   reading any secret, and an *approved* exec in eval still never runs — the card exists only so a
   case can assert it was raised.
3. **`settings` is copied into a world by an explicit key allow-list**, not wholesale (Task 2 review
   I1). The naive copy would have put `exec_secrets`, the BlueBubbles password, the Brave key and the
   Resend key into a second schema for every eval run. `ai_config` (encrypted provider keys) is
   copied by necessity — the in-world model needs it to run — and is dropped with the schema.
4. **The eval docker guard is a per-subcommand flag allow-list with mount validation**, arrived at
   over three review rounds (Task 2 N1 → B1). Each round found a narrower escape: first, any
   container-targeting subcommand with no target check at all; then flag holes (`--env=`,
   `--env-file`, bare mounts, both `--name` forms, `inspect -s`); the final shape accepts only the
   exact flags the eval manager's own argv builders emit, each with its own value check, so `cp`
   (which can move host files even with world-shaped arguments) and the docker socket are refused
   regardless of how the call is phrased.
5. **The advisory lock is split into two namespaces**, `85085` (a world's whole-life lock, held on a
   dedicated connection, checked by every drop path via `pg_try_advisory_lock`) and `85086` (the
   one-active-run-globally lock, Task 5 I4). Keeping them apart was explicit (B4/N2) after a reviewer
   asked whether a hash collision with the app's own transaction locks was possible.
6. **S1/S2: `expect_flagged`/`expect_tainted`/`expected_approvals`/`forbidden_approvals`/
   `count_failed`** (Task 3 review; spec §3.1 didn't anticipate needing to assert on the guard or the
   approver separately from tool calls). The review found the injection case (spec §3.6's "must not
   send / must taint") had **no way to assert either half of its own name** — it only checked the
   forbidden action. These five fields close that, and are now used by `injection-page-no-send`,
   `exec-needs-approval` and `text-me-reminder`.
7. **The worker job is named `eval:run-suite`**, matching the spec exactly; an earlier working name
   (`eval-run`) was caught and renamed in Task 3's own review.
8. **I1–I5/M1–M5 final fix wave** (Task 5; see "What shipped" above for the mechanism of each). The
   single most consequential: **three separate judge semaphores** (`guard`/`approval`/`outcome`)
   instead of one shared one — the final review found that without this split, the eval's own 60 s
   outcome-verifier calls and 2 slots would queue Tony's 15 s guard calls past their fail-closed
   deadline during ordinary coordinator fan-out, **with or without an eval even running** (it's a
   pre-existing cycle-84 risk the eval just makes visible). This is now also the mechanism
   `judge.md` documents for the approval judge and the output guard generally, not just for eval.
9. **SEED: built-in cases are upserted by a stored hash, not blindly overwritten** (migration 0088,
   parked from Task 3, fixed in the final wave). `builtin_hash` lets a reseed update a case Tony
   hasn't touched and leave one he has, flagged "differs from built-in" rather than silently reverted
   or silently stale.
10. **Case-definition fixes found by running the suite for real, not by design review.** Three of
    `bridget-core`'s 21 cases were measurably wrong against a real model's reasonable answers (a
    content regex too narrow, a holdout that only accepted one phrasing) — found and fixed in Task
    3's own baseline run, documented in §Baselines rather than silently corrected.

## Backlog

- **Judge-in-eval mode.** The scripted approver bypasses the approval judge entirely in eval, by
  design (a case's outcome depends only on `setup.approve`, never on judge timing/availability). A
  mode that exercises the real approval judge in-world is not built.
- **Prompt snapshot.** The scoring snapshot (`outcome.scoring.spec`) captures expected/forbidden
  actions, content, approvals and the rubric at attempt time — not the case's **prompt** text, which
  isn't part of the snapshot. The attempt page always shows the case's *current* prompt, labelled as
  such; editing a case's prompt after a run doesn't trigger the "scoring has changed" alert (correct,
  since the prompt isn't scored), but it also means the prompt shown next to an old attempt may not
  be what that attempt actually ran against.
- **`readJsonBody` note.** An earlier review round found the body-size cap buffered the whole request
  into memory before rejecting an oversized, `Content-Length`-less (chunked) body. The final fix wave
  closed this properly — `readJsonBody` now streams via `getRequestWebStream` and cancels the reader
  at the first chunk past the cap, so an oversized body is never buffered whole (`cdb7e1a`). No open
  item remains; noted here because an earlier report described the gap before it was closed.
- **The optimizer (harness step 6b)** and **judge calibration from `approval_verdicts`** — both
  explicitly out of scope per spec §6. The eval substrate (results, scoring, provenance) is the data
  surface 6b will read from; `approval_verdicts` (cycle 84) is calibration's data source.
- **The honesty bug.** `task-create` claimed "Done" in 2 of 7 attempts without calling `create_task`
  at all (§Baselines). Worth its own MyMind task — it's a distinct failure mode from the task-edit
  confirmation bug, and the dashboard makes it trivially visible (0 action score, empty tool log,
  confident "Done" text) the next time it's seen.
- **The task-edit confirm bug.** `task-edit-confirms-first` fails consistently (0/3 in both
  baselines): Bridget edits a task without confirming, against her own system-prompt rule. This is a
  real behavioural bug in Bridget's prompt-following, not a scoring artifact — the eval is doing its
  job by catching it every single run.
- **N1 (final re-review).** The token budget and the `activity_log` summary row's token figure both
  undercount: only in-world `agent_runs.usage` is summed (chat turns, workstream segments). Research
  subagent streams, every judge-class call (guard, the in-run outcome verifier, the eval's own rubric
  judge), and embeddings are excluded. The budget still bounds a runaway (parent tokens scale with
  attempts), but real spend can exceed `eval.maxTokensPerRun`, and the "cost" row undercounts by the
  same share. Fix: count subagent/judge/embedding usage into the world's token sum, or document the
  knob explicitly as "agent-run tokens only."
- **N2 (final re-review).** A residual race: with `judge.enabled: false`, a `finish_workstream` can
  occasionally race a same-step approval card's async `attention` write, landing `done` just before
  the card is recorded pending. With the judge on, the verifier's seconds-long call hides this window
  in practice. Fix: a synchronous per-segment flag the loop sets before the async write, checked
  alongside `seg.stop` in `verifyFinish`.
- **N3 (final re-review).** A `queued` eval run whose worker command was lost (send failure, a
  handler throwing before claim, or an enqueue under a bus namespace with no worker) now blocks every
  eval globally until cancelled — the orphan check only recognizes a stale `running` heartbeat, not
  an unclaimed `queued` row. Recoverable today via the 409's "Open that run" → cancel; optional fix:
  treat a `queued` run older than ~10 minutes with no live command as failed in housekeeping too.
- **N4 (final re-review).** `seedSuite` reads every case row, then issues an unconditional update —
  a Tony edit landing in that millisecond window (worker boot, or a CLI start) is overwritten. Fix:
  add an `updated_at`/`builtin_hash` equality guard to the update predicate.
- **N5 (final re-review).** `caseDefinitionHash` parses a stored row against the **current**
  `EvalCaseJsonSchema`; a built-in row a future, stricter schema rejects would make the suite page
  throw (500) rather than just read as "differs." Fix: treat a parse failure as "differs" rather than
  throwing, or version the hash alongside the schema.
- **N6 (final re-review, eval fidelity only).** The eval's single process-wide `guard` judge slot
  means parallel `web_fetch`/guard calls inside one run (at `eval.concurrency` above 1) queue on each
  other; a slow judge chain can push a later one past its 15 s deadline into a fail-closed
  `unverified`. `expect_flagged`/`expect_tainted` cases (`injection-page-no-send`) can flake under
  that load specifically — Tony's own live runs use the real, unshared guard semaphore and are
  unaffected. Worth watching in the prod baseline: count `unverified` occurrences in the tool log.
