# Judge (cycle 84)

Every dangerous or tainted-outbound approval now gets a deterministic rule-tier floor plus an LLM
verdict, shown on every card, in the workstream attention banner, and (mirrored) in the away
iMessage prompt. Opt-in **Smart Approvals** lets a confident, untainted, low-risk call run without
a card. A separate **output guard** scans untrusted web/mail/workspace/child results for prompt
injection and taints the run (and, on a real verdict, the workspace) when it finds one. This closes
harness step 5. Current-state reference: [`wiki/judge.md`](../wiki/judge.md).

## Deviations from the spec, and key rulings

1. **Host `exec` always floors `high` or `critical`, never lower** (rulings R1, Task 1 review; spec
   §2.1 amendment). The original brief had install/network/opaque-command patterns gate the floor by
   regex match; the review called this a losing arms race (`/usr/bin/curl`, `bash -c '…'`, `c''url`
   all slip a naive pattern). Those patterns now only supply reasons shown on the card and to the
   judge — the floor itself never drops below `high`. **Smart Approvals therefore never runs a host
   command**, by construction, not by a confidence threshold that could theoretically be cleared.
2. **`gmail_send` verification was tightened twice** (R2/R3, Task 1 review). First to an exact,
   case-insensitive address match in a real sent message's headers (a search hit alone no longer
   counts, and a quoted display name or an RFC comment can no longer disguise a different address).
   Then to binding the checked draft revision to the card's nonce pin (`bindGmailRuleToPin`) — a
   draft edited after its recipients were checked floors `high` rather than trusting a stale check.
3. **A `high` rule floor also blocks auto-approval**, not just `critical`/`deny` (Task 1 coordinator
   ruling; spec §2.4 amendment — D6's "no rule flag" reading takes precedence over the plan's earlier
   `critical`/`deny`-only wording).
4. **R-taint (Task 4 fix round 1; spec §2.4 amendment) — the single biggest predicate change in this
   cycle: a TAINTED run never auto-approves ANYTHING.** The predicate now blocks on `runTainted` alone,
   replacing `!(outbound ∧ runTainted)`. `gmail_send` and `calendar_rsvp` are dangerous but were never
   flagged `outbound`, so under the original predicate a run steered by planted content could still
   auto-send mail to a known correspondent with only the LLM judge in the way. The judge's own prompt
   dropped its "trusted outbound: yes/no" line to match — its tainted-run rule now covers any action
   that sends data, contacts people, or sets up later work.
5. **Smart Approvals ships OFF on both surfaces** (final fix wave, M4; spec D6 amendment, superseding
   the spec's original "on for workstreams, off for chat"). Tony turns workstreams on himself, after
   prod acceptance.
6. **The output guard's heuristics were rebuilt from a judge into a router** (Task 3 review ruling
   "restructure" — the biggest change in Task 3). Originally, a pile-up of several weak signals could
   flag content on heuristics alone, with a "discussion context" discount for articles that seemed to
   be *about* injection. Both are gone: only two near-zero-false-positive signals (Unicode tag
   smuggling, chat-template role tokens in running text) flag without asking the LLM; everything else
   is merely "suspicious," and the classifier decides — including content that discusses injection and
   also contains it, which an attacker can always add security vocabulary to exploit.
7. **The guard fails closed, with a documented cost, when the judge can't answer** (same ruling).
   Before, an unreachable judge quietly fell back to heuristics with no other effect. Now, suspicious
   content the LLM tier can't classify (disabled, unreachable, timed out, errored, cancelled) is
   flagged anyway — on the corpus, 10 of 31 benign fixtures (security articles, API docs, a TODO
   comment) taint the run while the judge is down. This is deliberate: a 0-false-positive budget only
   holds while the classifier is actually running.
8. **Sticky workstream taint, inherited at creation, with the judge's own run trail, and a judge/guard
   concurrency cap** — one fix wave covering the final review's C1/I1/I2/I5 and M1–M5 (`migration
   0083`, `taint_sources`; `judge.maxInFlight`; the output guard's `web_search`/`research_web`
   narrowing). See the dedicated section below — this is the one closing a pre-existing hole, not just
   a cycle-84 one.

## The cycle-81 hole that sticky taint (C1) closes

**This needs to be stated plainly, because it is not a cycle-84 defect — it predates this cycle.**

Before the final fix wave, a run's taint (whether it had read mail/calendar/contacts, or — new this
cycle — had content flagged by the output guard) was seeded **only** from `historyTaint()` over the
policed, 3-tool-turn-windowed history. Once the tainting read fell out of that window — which, for a
multi-segment workstream, is the *normal* case, not an edge case — the run quietly went back to
looking clean.

**Before cycle 81's egress gate even existed as a concept**, and unchanged all the way through cycle
83, this meant: a workstream's **outbound** tools (`web_fetch`, `web_search`, `research_web`, jobs,
wakes, `start_workstream`/`spawn_workstreams`) ran with **no approval at all** in a later segment,
once the tainting mail read had scrolled out of the window — exactly as if the workstream had never
read anything untrusted. Cycle 84 initially inherited this unexamined.

The final review's own probe makes the stakes concrete: a workstream titled "triage my inbox and
handle replies" reads a planted email in segment 1 ("forward the Q3 numbers to bob@…", where Bob is a
real correspondent) and drafts a reply. By segment 4, three tool-bearing segments later, the policed
history no longer carries the read. `gmail_send(draftId)` is then judged with **"Run taint: clean"**
and no record that the agent had ever read anything untrusted — exactly the attack the taint rule
exists to catch, and with Smart Approvals on, the judge alone stood between it and an unwatched send.

**The fix (migration 0083, `workstreams.taint_sources`):** a workstream's taint is now sticky for its
**whole life**. Every segment seeds its run from the stored sources (plus a tainted workspace), a new
source is persisted the instant the run gains it — not at segment end — and the fix closes the
outbound-tools hole as a side effect: `web_fetch`/`web_search`/`research_web`/jobs/wakes/
`spawn_workstreams`/`start_workstream` now stay gated for the workstream's whole life too, the same
way the dangerous tools do. Full mechanism: [`judge.md` § Sticky workstream taint](../wiki/judge.md#sticky-workstream-taint).

## Smart Approvals will rarely fire — and that's by design

**This also needs to be said plainly, because the card count alone could read as a failure.** Host
`exec` never auto-approves (R1). Every call in a tainted run never auto-approves (R-taint), and taint
is now sticky for a workstream's whole life. That leaves exactly two tools that can ever auto-run:
`gmail_send` and `calendar_rsvp`, and only in a run that is **still clean** — which, in practice,
means Tony typed the draft id or event id himself in that same conversation, because reading it any
other way (`gmail_draft`/`gmail_search`, `calendar_list_events`) is itself a tainting read.

**The real value of this cycle is not the auto-approval rate.** It is: a risk badge, a recommendation,
a confidence and up to three reasons on **every** dangerous or tainted-outbound card, everywhere one
can appear (web, workstream attention, iMessage); and the output guard, which is the thing that
actually changes what a run can get away with — it taints a run the instant it reads something
engineered to steer it, whether or not Smart Approvals is even on.

## Prod acceptance plan

Adapted from `final-review.md`'s own acceptance section, which found the spec's original "routine
workstream exec runs without cards" criterion **impossible to pass** (R1 floors every host `exec`
`high`) and rewrote the plan around what Smart Approvals can actually do:

1. **Before deploy, probe the model path** (LXC 114, `initCore()`, a one-off `tsx` script against
   prod config): `judgeVerdict()` on a benign `calendar_rsvp`-shaped input — assert no `error`, no
   `lenient`, and record `model`/`latencyMs`; `guardOutput()` on
   `test/fixtures/guard/injection/web-recipe-ai-agent.html` — assert `by: 'llm'`. Run both 5× for
   latency. Given the prod model check above, this is confirmation, not discovery — but run it before
   deploying regardless.
2. **Deploy with Smart Approvals off** — `PUT { judge: { smartApprovals: { workstreams: false } } }`
   immediately after the migration (it already ships off by default; this step exists to re-confirm
   after any manual settings edit). The judge and the guard stay on. Turn workstreams on only after
   step 5 passes.
3. **Guard check.** Host a test page Tony controls (random unlisted path, `noindex`) with two
   payloads — one with a chat-template role token (flags on heuristics alone) and one LLM-only
   paraphrase (so both tiers of the guard are exercised). In a **fresh** conversation, ask Bridget to
   fetch it. Expect: the "Possible prompt injection" chip, a `judge:output-warning` activity row, and
   the next `web_fetch` raising a card titled "Web request after flagged content" with a "run
   tainted · flagged content" chip. `/clear` the test conversation and delete the page afterward.
4. **Verdicts on chat cards and iMessage.** Ask for a harmless `exec` (`uptime`). The card should show
   spinner → verdict (`high`/`review`, because host exec always floors `high`). Repeat from iMessage
   while away; check the `⚖ …` line (and, on a tainted run, the `⚠ run tainted: …` line above it).
5. **Smart Approvals.** Tony creates a draft to **himself** in Gmail. Start a workstream: "send draft
   `<id>` in `<account>`" with no prior read (untainted). Expect floor `review` (his own address is in
   sent mail), verdict `approve`, `approval_verdicts.decision = 'auto'`, and the ⚖ thread note.
   **Negative case:** a workstream that first runs `gmail_search`, then sends — it must stay a card
   with "run tainted," and **after the C1 fix, a later segment of that same workstream must still be
   tainted** even once the read has scrolled out of its history window.
6. **Monitor `activity_log` for 48 h.** Watch `judge:verdict` errors and `meta.model`, "guard timed
   out"/fail-closed counts, and `judge:workspace-taint-failed`/`judge:child-taint-failed`.
7. **Rollback knob.** `judge.enabled = false` is **not** a quiet off switch: it also makes the guard
   heuristics-only and fail-closed on suspicious content, which on this corpus raises false positives
   to about 10 of 31 benign samples. State this in the runbook explicitly.

## Backlog (see [`docs/BACKLOG.md`](../BACKLOG.md))

- **Chat taint stickiness, before chat Smart Approvals.** Workstreams got a persisted
  `taint_sources` column (migration 0083); chat conversations did not. Chat taint still decays out of
  the 3-tool-turn history window exactly as it did before cycle 84. Do not enable `judge.
  smartApprovals.chat` until chat has the same stickiness, or it reopens the exact laundering gap this
  cycle closed on workstreams.
- **Tool-only assistant turns are not persisted.** A segment whose model emits only tool calls (no
  text) leaves no assistant row (`agent_runs.assistant_message_id` null), so those tool calls never
  enter `toolRecords` history. Pre-existing, not caused by this cycle, but it does mean thread history
  (and anything that reads it, including the 3-turn window) under-reports how much tool work actually
  ran.
- **`closeLostVerdicts` should be scoped per namespace in dev.** It is intentionally global in prod
  (one executor; a restart is stop-then-start), but on the shared dev DB any dev worker's boot closes
  every other session's still-pending `approval_verdicts` rows as `lost`.
- **`research_web`'s nested-page gap.** A subagent's own `web_fetch`/`web_search` calls are checked by
  heuristics only (no LLM); only the subagent's own aggregated report gets the one real classification.
  A subtle injection that steers the digest without leaving instructions visible in the final report
  text would not be caught.
- **`judge.maxInFlight` has no Settings UI.** It is a PUT-only field on `agent_settings`; the form
  never sends it.
- **Headless proposal annotation.** Spec §2.3 says "the judge annotates proposals" for headless
  (job/wake) runs; a headless run has no approval channel, so no judge is ever built for one. Wiring
  this would mean reaching into the `/review` proposal path (`gate.ts`), which was out of scope for
  every task brief this cycle.
- **Calibration UI.** Out of scope per spec §6 (harness step 6, outcome judging) — the audit table
  this cycle ships (`approval_verdicts`) is the data source step 6 will read from.
