Systems Feasibility · MyMind · 2026-08-10

Going multi-user isn't a feature. It's an authorization re-architecture.

Feasible — and cheaper than it looks — because of how the app is built, not what it stores. The layering is clean and better-auth is already multi-user-ready. The data model and the trust model are purely single-user: today, "authenticated" means "owner of everything."

Not ready — the data & trust model

0 tables know who owns them

No domain table carries an owner. Every query is corpus-wide. Any second account reads and edits everything.

bridged by~6–8cycles
Ready — the architecture

One clean seam to scope

Thin handlers over ~171 service functions. better-auth, per-request MCP, one storage driver — all already N-user-shaped.

02

Why it's more feasible than it looks

the architecture is on your side

better-auth is already multi-user

Sessions, accounts, OAuth-token→user binding, PKCE + consent — all N-user-ready. The MCP lane already resolves a real userId… which buildMcpServer() then throws away.

The enforcement seam exists

Handlers are uniformly thin; nearly everything funnels through server/services/. Scoping is wide but mechanical — thread an ownerId, back it with Postgres RLS.

Stateless where it counts

The MCP server is built fresh per request. The live-bus comment already sketches the fix. Storage funnels through one driver with no path-based serving.

The frontend is clean

No "Tony" hardcoded anywhere in app/. Auth middleware is a pure session check. The API-keys page is already shaped as personal data.

03

The blockers, ranked

everything is downstream of #1
1

No tenant column, no ownership predicate, anywhere

Every list / get / search / update / delete is table-wide across documents, memories, tasks, projects, sessions, images, conversations, activity, search. The rest of this list is downstream of this one fact.

Blocker
2

api_tokens are userless skeleton keys

No owner column; middleware grants full access with no identity. Every mm_ token — ShareX, cc-hook, MCP — is whole-corpus access. A leaked token is a god-token.

Blocker
3

Agent exec = root RCE on the shared host

/bin/sh as root, no cwd jail, all decrypted service secrets injected into the child env, and the prompt hands the model the DB-access command. Incompatible with untrusted users; per-tenant sandboxing is a near-rewrite. v1 answer: exec admin-only.

Blocker
4

Skills are cross-user prompt injection

One global namespace; agent-authored skills go live immediately with only structural validation. One user's skill becomes live instructions inside every other user's agent.

Blocker
5

No roles

Any authenticated principal — including any bearer token — can rewrite AI keys, exec secrets, the shared persona, and fire /api/admin/* LLM-cost batch jobs over everyone's data.

Blocker
6

All three SSE surfaces are global

The change bus leaks ids and slugs to every client. Clipboard SSE pushes full message contents to any subscriber with zero ownership check. Agent-activity broadcasts tool summaries globally.

Blocker
7

activity_log stores raw model payloads, unowned

Full prompts and document content persisted with no owner, listed globally — one user's private content readable by all.

Blocker
8

Account lifecycle is a bootstrap hack

ALLOW_SIGNUP toggle into a shared corpus. No invites, no email verification, no password reset. There is no safe way to add a second account today.

Blocker
9

Global config singletons + zero metering

One ai_config with the operator's keys, one persona, one observability config. No per-user cost attribution, budgets, quotas, or billing exist anywhere in the repo.

Major
10

Global uniqueness = collisions, injected writes, and oracles

Two users can't both own notes/inbox.md. A hostile client can inject into another user's session via a colliding external_id. Two tenants cloning the same repo merge into one project.

Major
Cross-tenant writes people forget about — not just read leaks
  • The memory relations judge pools neighbors across owners and can auto-archive another user's memory via LLM "supersede."
  • Enrichment cross-pollination: the filing prompt sees all projects (files your doc into my project); the image tag library unions everyone's tags.
  • Blob dedup is a cross-tenant existence oracle, and un-sharing an image doesn't revoke it (immutable 1-year cache + slug reuse).
Operational blockers for hosting anyone
  • No rate limiting; no quotas; vision + embedding spend on every upload with no cap.
  • UMAP recompute is synchronous and event-loop-blocking; /api/graph/recompute is a free DoS button.
  • Crons have no locks — a second replica silently double-runs every job and doubles LLM spend.
  • Backups are a manual pg_dump; monitoring emails itself from inside the process it monitors.

05

Three paths

pick by intent, not by ambition
★ Start here
Path 0

Instance-per-user

days · near-zero code

Don't multi-tenant the code — multiply the instances. Proxmox is already the substrate: clone an LXC per person, own DB, own storage, own subdomain. The LXC boundary per-tenant-sandboxes exec by construction — the exact property the shared codebase can't offer. Validates whether interest survives contact with reality, at zero corpus risk.

Path A

True multi-tenancy, invite-only

~6–8 cycles

For trusted-but-real users on one instance. In dependency order:

  1. Identity & roles — api_tokens.user_id, role column, buildMcpServer(userId), invites + email verification via the existing Resend key.
  2. Tenancy migration — owner columns on ~20 tables, composite uniques, backfill to the bootstrap user.
  3. Scoping — thread ownership through services; enable Postgres RLS as backstop; ship a two-user isolation test harness.
  4. Async & live — per-user cron slicing + budgets, scoped publishChange, per-user galaxy, per-user badges.
  5. Frontend — user menu / sign-out, role-gated nav, settings split, per-account cache + cookie scoping.
  6. Ops hardening — rate limiting, quotas, off-box backups. Exec + skills authoring: admin-only.
Path B

Hosted SaaS

a different product

Everything in A, plus: leave the homelab (managed PG, S3, orchestration), metered AI + billing (nothing exists), exec removed or per-tenant microVMs, multi-instance safety, compliance (per-user export/delete — impossible today), abuse moderation for the public image host, real on-call. Only worth it if this becomes a business.

06

Decision forks

settle these before any spec

AI keys: operator-paid or BYO?

Global registry with per-user budgets, or per-user keys? The entire onboarding + settings IA forks on this.

Exec capability?

Admin-only (ships Path A) vs per-tenant sandbox (XL) vs removed for tenants.

Blob store?

Keep global dedup + refcounted GC (accepts the existence oracle) vs per-user key prefixes (loses dedup).

Enforcement depth?

Service-arg threading alone, or + Postgres RLS. One missed WHERE clause anywhere is a silent corpus leak.

07

Recommendation

Now

Path 0 for the interested people. Days of ops work; validates demand; gives each person the same trusted single-user product you actually built — including their own exec.

This month

Add api_tokens.user_id + a role column anyway. Small effort — it closes the god-token and settings-takeover risks even on the single-user instance. Keep ALLOW_SIGNUP off.

If demand is real

Path A behind invites, exec + skills admin-only, RLS on. Budget ~6–8 cycles. The work is wide and mechanical, not deep.

Only with revenue

Path B. It is a re-platform, not an upgrade — don't drift into it by accident.
